# HFT 公众号文章生产流程

把 HFT 公众号文章从资料核对推进到可审阅、可追溯的 Word 和飞书成稿。核心原则是：**飞书成稿管公开表达，官方资料管事实，本地 Markdown 管可编辑内容和核对记录，Word 是交付副本。**

## 必需协作 Skill

- **正文起草或改稿：**必须使用 `hft-write`。
- **用户要求从 IMA 取材：**必须使用 `ima-skill`，确认拿到真实资料后再写。
- **创建或编辑 Word：**必须使用 `documents:documents`。
- **创建、读取或编辑飞书文档：**必须使用 `lark-doc`，并遵守其认证、局部读取和块级更新规则。
- **OpenAI / Codex 事实核对：**必须使用 `openai-docs` 或 OpenAI 官方资料。

## 一、确认范围

开始前确认：

- 目标文章、目标读者和文章状态。
- 本轮是内容改写、结构调整、截图补充、Word 生成、飞书排版，还是仅修格式。
- 当前公开正文是否已经存在于飞书。
- 用户指定的基准稿和禁止改动的内容。

用户说“不要改语言”“只改格式”时，立即锁定正文措辞。只允许改变块类型、图片、标题层级、必要换行和用户明确点名的格式。

## 二、确定内容权威顺序

同时存在多个版本时，按下列职责判断，不按文件修改时间盲目覆盖：

1. **飞书当前正文：**决定已发布或待发布正文的结构、措辞、段落和续写位置。
2. **官方文档与真实测试：**决定命令、模型、价格、限制、功能和平台规则是否准确。
3. **本地 Markdown：**保存可编辑正文镜像、来源、核对时间、待核对项和同步记录。
4. **Word：**用于审阅、导入或交付，不反向覆盖飞书；Word 中独有修改只能作为候选内容。

飞书与本地稿冲突时，先列出差异。无法判断差异是用户主动修改还是导入损坏时，停止合并并询问，不静默覆盖任一版本。

## 三、读取项目和来源

1. 阅读项目 MOC、栏目定位、写作原则、选题库、现有草稿和来源记录。
2. 用户指定 IMA、公众号、PDF、网页或项目材料时，先取得真实内容。
3. 涉及数字、价格、模型名称、命令、API 限制、平台规则和协会成果时，逐项记录来源与核对时间。
4. 无法确认的内容标记“待核对”；正式发布前完成核对或删除。
5. 参考公众号只学习信息组织和呈现方式，不复制其模板或大段原文。

## 四、建立修改基线

- 检查 Git 状态，识别与本任务无关的修改。
- 大规模合并或改写前，如用户要求提交或当前流程已约定快照，只提交目标草稿。
- 不暂存、不撤销、不格式化、不提交无关文件。
- 记录飞书当前 revision；后续写入前确认它没有被他人更新。

## 五、比较、合并和改稿

1. 先比较草稿，列出重复、互补、冲突、待核对和应保留段落。
2. 先给出结构判断，再开始合并；不要边阅读边整体重写。
3. 使用 `hft-write` 执行正文改稿。
4. 保留已经形成的文章风格，不用通用模板覆盖用户认可的成稿。
5. 中文界面术语以中文为主，首次出现时附英文括注，后文沿用中文。
6. 提示词示例写清目标、范围、限制和验收标准。

公开正文与内部生产信息分开：核对时间、来源明细、待核对项和同步记录保存在本地稿或来源记录中；除非用户要求，不把内部清单放入飞书公开正文。

## 六、规划和处理截图

- 先冻结正文结构，再建立截图清单。
- 每张图只承担一个主要任务：入口、操作、状态或结果。
- 记录编号、所属章节、图注、来源、当前状态和是否需要打码。
- 优先使用用户真实操作截图；官方截图需保留来源，不使用生成图片冒充产品界面。
- 中文截图使用中文主称；没有中文界面时不伪造中文 UI。
- 检查账号、邮箱、API Key、Token、余额、用量、真实路径和项目隐私。
- 用户采用“三张一组”提供截图时，按组插入、核对并汇报下一组需求。

图片放在首次解释对应操作的段落之后。图注只说明图片展示的状态，不重复整段正文。

## 七、生成 Word 初稿

使用 `documents:documents`：

- 保留标题层级、段落、列表、代码块、图片和图注顺序。
- 清除所有节的页眉、页脚、页码及其继承关系。
- 命令、提示词、配置和流程示例使用独立代码样式。
- 渲染 Word 全部页面并检查分页、图片清晰度、代码换行、标题层级、孤行和溢出。
- Word 是交付副本，不是正文权威来源。

## 八、创建或更新飞书正文

使用 `lark-doc`：

1. 读取最新飞书正文和 revision。
2. 精准编辑优先使用带 block ID 的局部更新；不要用整篇覆盖处理局部格式问题。
3. 普通说明保留为正文段落。
4. 以下内容使用飞书原生代码块：命令、提示词、配置、路径、可复制链接集合、代理链路和验证指令。
5. Word 导入把长提示词拆成多个段落时，按原顺序合并为一个原生代码块。
6. 写入后重新读取目标章节，确认文字、顺序、块类型和图片都正确。

用户要求飞书在线文档时，飞书原生正文是主要交付物，不能只上传 `.docx` 代替在线文档。

## 九、系统性复核

不要只修用户指出的一处。对全文执行两轮检查：

1. 按候选清单逐项核对代码块、图片、图注、标题和术语。
2. 从文首重新扫描到文末，确认没有同类遗漏。

格式修复任务还必须满足：

- 修改前后普通正文措辞不变。
- 代码块内部大小写、标点、路径、参数和换行不变。
- 飞书代码块数量与本地 Markdown fenced code block 范围能够对账。
- 飞书最终结构同步回本地 Markdown，避免下次导入复发。

最终交付前读取并执行 [production-checklist.md](references/production-checklist.md)。

## 十、停止条件

出现以下情况时停止写入并说明阻塞：

- 用户要求从 IMA 或指定来源取材，但尚未取得真实内容。
- 无法读取飞书当前正文或确认最新 revision。
- 编辑期间飞书版本发生变化，可能覆盖他人修改。
- 多版本存在影响含义的冲突，且无法判断用户意图。
- 关键事实缺少官方或实测依据。
- 用户只授权格式调整，但任务需要删除、重排或改写正文。
- 飞书写入后无法复查，或本地源稿无法可靠同步。

## 十一、完成汇报

完成时只报告可验证结果：

- 本地 Markdown、Word 和飞书文档的位置。
- 飞书 revision 和本轮修改范围。
- 已核对来源与仍需复核的项目。
- 截图数量、隐私检查和代码块复核结果。
- 未执行或无法完成的步骤及原因。

不要把“命令执行成功”当成“文档视觉交付完成”。未检查飞书实际结构或 Word 渲染结果时，不得宣称全部完成。
