围绕 HypoWeaver-Qwen 评估论文与架构决策。默认保持现有架构，只在发现可验证的能力缺口时提出最小、可逆的变化。

## 架构基线

把系统理解为相互连接但职责不同的结构：

- 证据层：保留文献、政策、数据和方法证据的来源与矛盾。
- 假设与机制结构：连接主张、机制、变量、边界条件和证伪条件。
- 研究设计树：保存可比较、可回退的操作化、数据和识别方案。
- 审查与版本化研究记忆：把问题转成可执行任务，保留成功与失败历史。

图负责多对多关系，树负责分支探索，版本化记忆负责耐久决策；不要把三者强行合并。

## 标准流程

### 1. 恢复当前状态

从活跃文件中确认：

- 当前已接受的第一版边界；
- 已读论文及其状态；
- 尚未解决的架构缺口；
- 已否决、仅参考或仍处于实验态的方案；
- 当前最合理的下一步。

不要把旧设计稿中的候选项当成当前结论。

### 2. 分离三类陈述

始终明确标注：

- `论文事实`：来源明确陈述或验证的内容；
- `分析推断`：根据论文机制做出的解释；
- `项目提案`：HypoWeaver-Qwen 的设计选择。

不得把推断或提案写成论文结论。解释关键术语时加载并遵循
`paper-terminology-translation-explanation`，不要在本 Skill 内复制术语规则。

### 3. 执行非增生审查

按顺序回答：

1. 当前架构出现了什么可观察的失败或缺口？
2. 现有角色、对象、字段、状态流转或人类闸门能否处理？
3. 论文验证了完整机制，还是只描述了想法或其他子系统？
4. 最小变化是什么？
5. 同步、来源追踪、权限、测试、人工审查和恢复成本是什么？
6. 哪个实验能证明变化必要且有效？

始终保留 `no_change` 基线。按以下状态分类：

- `no_change`
- `reference_only`
- `clarify_existing`
- `experiment_minimal_delta`
- `proposal_candidate`
- `reject_or_hold`

只有后两类可以形成架构变更提案。

### 4. 映射到实证研究

检查机制能否覆盖：

```text
问题定义 → 文献与政策证据 → 理论机制 → 假设与变量
→ 数据可得性 → 识别策略 → 执行 → 稳健性与证伪
→ 审查修订 → 研究记忆
```

涉及绿色金融时，再检查政策时间、变量操作化、公开数据、内生性、异质性和复现条件。可用“绿色信贷政策是否促进企业绿色创新”作为测试案例，但不要把绿色金融模块强加给无关讨论。

### 5. 形成可审查结论

默认按以下顺序输出：

1. 三句话复原论文或问题；
2. 论文事实、推断与项目提案；
3. 非增生审查结果；
4. 对当前架构的最小影响；
5. 可执行验证方案；
6. 决策状态与仍开放的问题。

需要 ACP 时使用最小字段：

```yaml
proposal_id:
problem:
current_coverage:
proposed_delta:
source_evidence:
expected_benefit:
risks:
validation:
acceptance_criteria:
status: experimental | proposed
```

## Obsidian 写入边界

讨论、同意观点、说“可以”或要求继续，都不构成写入许可。

任何创建、编辑、重排或删除 Obsidian 内容的操作都必须加载并遵循
`discuss-confirm-write-obsidian`：

1. 先读取目标文件的相关段落；
2. 展示包含目标文件、位置、操作方式和具体要点的写入预览；
3. 等待用户在预览之后明确回复 `确认写入`；
4. 仅执行预览中批准的最小增量；
5. 核验文件、章节和未授权内容。

没有收到预览后的 `确认写入` 时，只返回讨论稿或候选结论，不写文件。

只把已接受决策写入 `当前架构设计.md`。实验、候选、否决和待定项留在
`架构演化工作稿.md` 或相应记录中，并保留理由。不得自动创建新版本、更新图表或重写汇报稿。

## 质量底线

- 先检查活跃文件，再提出变化。
- 不因论文出现一个名词就创建新 Agent、层、图、索引或服务。
- 保留反证、失败结果和回退路径。
- 不把相关性写成机制，不把不可取得的数据写成可用。
- Reviewer 必须产生可执行问题，不用措辞修饰掩盖科学缺口。
- 明确报告 `no_change`；没有架构变化也是有效结论。
