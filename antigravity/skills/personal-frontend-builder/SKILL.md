# 适合用户的前端构建

先判断用户要的是**实际实现**，还是**可复制的开发提示词**。要求实现时直接推进实现；不要把写提示词、生成概念图或等待设计确认设为固定前置步骤。

## 确定任务

读取当前项目指令、相关页面、现有组件和可用的真实数据或截图。用简短的工作判断明确：谁在用这个页面、要完成什么任务、输入与输出是什么、哪些内容和交互必须保留。只有目标或关键约束无法从现有材料确定，且会显著改变结果时才问用户；其他设计细节自行作低风险选择。

现有产品的设计系统、用户提供的参考图和明确要求优先。用户要求统一个人软件风格，或新产品没有既定视觉语言时，再读取 [个人视觉参考](references/personal-visual-system.md)；不要把该配色强加到已有品牌或其他团队项目。

## 实际构建

- 先排信息层级，再决定颜色和动效。为每个重要页面给出真实任务入口、可理解的内容与状态；不要用空白仪表盘、虚构指标或纯装饰卡片充数。
- 桌面导航保持稳定且尽量单行可辨；充分利用可用宽度。列表、详情和操作区各有明确位置，弹层不要挡住主要内容或让用户陷入多层滚动。
- 移动端检查纵向浏览与触控路径，避免横向溢出、固定面板挡内容，以及嵌套滚动抢手势。
- 数据型界面区分已核验、待处理、证据不足和失败状态；真实数据不足时如实呈现，不补造结果。
- 遵循项目现有技术栈，优先复用组件与素材。只在解决真实视觉问题时使用生成图片或新增动效；导航、表单、表格和操作保持可运行的原生前端元素。

完成后运行与改动相关的检查，并打开实际页面。核对主要桌面尺寸及任务涉及的窄屏，操作至少一条主要流程；检查中文长标签、可见焦点、对比度、加载与错误状态。向用户说明哪些结论来自实际页面，哪些仅由代码或构建支持。

## 只要求优化提示词时

交付一段可直接交给前端开发 Agent 的中文任务说明，按需包含：用户任务、目标页面与内容、输入输出、交互与状态、视觉参考、响应式要求、数据与证据边界、允许改动的范围、验收方法。填入当前项目已核实的信息；缺失但不阻塞的细节标为可由执行者判断。不要把通用口号、长篇角色设定或重复审批流程塞进提示词，也不要擅自实现代码。
