# Obsidian 讨论—确认—写入协议

把讨论同意与文件授权严格分开。本 Skill 只管理 Obsidian 写入边界，不决定论文或架构内容本身。

## 默认状态

默认：

```text
Obsidian write status = OFF
```

允许读取笔记、讨论、修订候选结论和准备预览；禁止创建、追加、编辑、删除、重排、更新图表或版本号。

“可以”“行”“继续”“同意”“这个方向可以”等只表示继续讨论，不是写入授权。读取文件也不授权编辑。

## 写入协议

### 1. 明确写入意图

用户提出保存、更新、新建、整理到原文档等要求后，先进入预览阶段，不立即写。

### 2. 展示预览

使用：

```text
【Obsidian 写入预览】

目标文件：
操作：新建 / 追加 / 局部修改 / 删除 / 重排
写入位置：
拟新增或修改的标题：
拟写入要点：
依据：
是否修改原有文字：
是否更新 Mermaid 或其他图表：
是否更新版本号：
明确不写入：
```

删除、重写或重排时还要写明：

```text
具体受影响段落：
原因：
对现有结论的影响：
恢复方式：
```

预览必须具体到目标、位置和内容范围。不能用“按刚才讨论写入”代替。

### 3. 等待精确确认

只有用户在看到当前预览之后明确回复：

```text
确认写入
```

才执行写入。提前说过、针对旧预览说过或只表达赞同，都不生效。

确认只覆盖当前预览中的文件、操作和内容。用户修改了目标或内容时，展示修订后的预览并重新等待 `确认写入`。

### 4. 执行最小变化

- 先读取目标文件的相关段落。
- 优先局部补丁，不整篇重写。
- 只写预览内确认的内容。
- 保留既有历史、标题结构和术语。
- 不顺手增加相关但未授权的内容。
- 删除、重写、重排、图表和版本变化必须在预览中明确出现。

每一行变化都必须能追溯到获批预览。

### 5. 核验

写入后检查：

- 文件存在；
- 内容位于获批位置；
- 原有内容没有意外丢失；
- 没有引入未授权内容；
- Markdown 标题、链接、表格和 Mermaid 块完整。

只报告：

```text
实际修改文件：
实际修改章节：
是否修改原文：
是否更新图表：
是否更新版本号：
明确未写入：
核验结果：
```

## 异常处理

若发生未授权写入：

1. 立即停止后续修改；
2. 报告文件和实际变化；
3. 在能安全恢复时恢复写入前状态；
4. 核验恢复结果；
5. 回到预览与 `确认写入` 流程。

不要用第二次大改掩盖第一次越权。

## 最终门禁

写入前必须同时满足：

- 用户已明确提出写入意图；
- 当前目标和内容已完整预览；
- 用户在该预览之后回复了 `确认写入`；
- 插入或替换位置已知；
- 删除、重排、图表和版本变化已单独列出；
- 写后核验方法已确定。

任一条件不满足时保持只读。
