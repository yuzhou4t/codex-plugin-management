# 界面方向对齐

先对齐方向，再动手画。目的是避免框架来回换（例如做了 11 个原型，整体框架换了大约 9 次，每换一次都要补一串修补）。

## 硬规则

1. **先写一页简报，用户点头再动手。**
   - 目标：这个界面要让谁相信什么、做成什么。
   - 关键画面：3 个关键画面，每个画面不滚动就必须看到的内容。
   - 约束：目标屏幕尺寸（比如投影 1280×720、1440×900）、深色和浅色模式、语言、不能改的东西。
   - 参考：1–3 个用户喜欢的参考，以及具体喜欢它们哪一点。
   - 非目标：比如「不做聊天界面」。
2. **比较 2–3 个方向，只选一次。** 方向之间要在信息结构上不同（向导、工作台、文档），而不是只换颜色；里面放真实内容和真实数字。如果已安装 prototype skill，用它来做这些一次性原型。
   - 为什么：只在外观上不同的原型没有比较价值。
3. **记下选择和理由。** 以后想换方向，必须说明简报里哪一条变了；简报没变，方向就不变。
4. **定下之后只做打磨。** 间距、密度、颜色可以调，外壳不换。真要推倒重来，先说清楚代价（比如「大约要花 1 天修补」），让用户明确拍板。
5. **保护用户自己的改动。** 动手之前先拉取并 diff 用户最新的分支；用户的改动只合并进集成分支，绝不重置、覆盖或重新移植；每次合进用户预览的分支之前先打回滚 tag。
   - 为什么：差点覆盖用户前端的事故，往往就发生在「我重新移植一遍」的时候。
6. **按测量加截图验收。** 在每个目标尺寸下用脚本检查：页面不意外滚动、元素不重叠、内容宽度利用率达标、没有大块空白、文字不溢出。验收前把假内容清掉（示意聊天、「未接入」标签、样例数据），改用真数据或明确的空状态。

## 交接格式（前端 Agent 交给架构师）

- 写明 commit 或分支、截图路径、逐项检查结果、哪些只用假实现验证过、已知问题。
- 架构师验证并部署到预览环境之后，才告诉用户可以看了。没验证不说完成；如果全局 AGENTS.md 里有这条规则，以它为准。

## 检查清单

- [ ] 简报已得到用户确认
- [ ] 比较了 2–3 个结构不同的方向，选择和理由已记录
- [ ] 已和用户最新的分支 diff，打了回滚 tag
- [ ] 每个目标尺寸都有测量结果和截图
- [ ] 假内容已清掉
