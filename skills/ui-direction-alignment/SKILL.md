# 界面方向对齐

把含糊的观感要求转成可观察的界面结果，减少反复推倒布局。现有设计规范、用户最新要求和已接受的画面优先；本流程补充具体前端实现 Skill，合并相同检查，避免多轮重复确认。

## 明确方向

1. 从当前页面、用户参考和实际内容中说明：谁在用、主要任务、关键首屏内容、目标尺寸、要保留的交互，以及参考中具体想借鉴的部分。规模小时用几句话即可，复杂改版再写简报。
2. 目标和约束已足够清楚时直接实现。只有几种解释会产生明显不同的成品、现有材料仍不能确定时，提供最小的可比较样例：例如同一内容的 2–3 个结构方案、关键帧或一段实际交互；只询问会改变结果的选择，并继续独立工作。
3. 记录选择依据和保留项，沿用已有决定。后续修改先定位是内容、构图、运动、密度还是运行环境的问题，保留已认可部分；用户的新要求可以改变方向，不把旧选择当作永久冻结。

## 实施与保护已有工作

- 动手前核对当前 Git 状态、相关分支和用户已有修改。需要同步远端时先比较差异，再按当前任务整合，保护未提交和未跟踪内容。
- 延续项目现有技术栈与设计系统，围绕真实任务比较信息结构，而不只比较配色。大幅替换已有实现前说明影响，并采用与风险相称的恢复方式；普通调整沿用正常版本保存流程。
- 样例数据可以用于方向讨论，但要标明性质；正式验收使用实际数据或明确空状态。必要的“未接入”、失败和加载提示要反映真实能力，不能为了截图隐藏未完成状态。

## 实际界面验收

- 在约定的屏幕尺寸和实际运行环境中检查关键画面，操作一条主要流程；核对溢出、遮挡、文字可读性、空间利用和滚动行为是否符合页面用途。长页面可正常滚动，不将零滚动或固定利用率设为所有页面的指标。
- 按任务需要结合截图、测量与实际交互。构建成功、静态截图和真实运行各证明不同内容；未执行的检查明确标注。
- 交付说明版本或分支、可查看的位置、主要可见变化和剩余问题。用户要求运行预览或更新本地安装时完成相应部署；只要求源码修改时，按已授权范围交付。
