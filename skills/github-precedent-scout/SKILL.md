# GitHub Precedent Scout

搜索并核查真正可复用的 GitHub 先例，帮助用户在采用、依赖、参考和自行实现之间做决定。只要求调研时交付路线判断；要求实现时，侦察是其中一步，选定合适方案后继续完成已授权实现。

## 触发规则

自动触发：

- 用户准备从零开始一个新项目、产品、工具或独立体验；
- 用户正在头脑风暴，且选用成品、模板、库或自行实现会实质改变路线；
- 用户明确要求先看 GitHub、开源方案、前人实现或避免重复造轮子。

不自动触发：

- 已定位的 bug 修复、日常维护或小范围迭代；
- 当前项目已经明确指定实现、依赖或架构；
- 只需解释现有代码、整理文档或做本地验收。

自动触发不等于自动采用。搜索完成后仍按证据给出复用分类和路线选择。

## 工作流

### 1. 提炼目标

用一句话明确：

- 要解决的问题或目标体验；
- 必须满足的技术与许可约束；
- 用户要找完整成品、模板、库还是设计参考。

只有缺失信息会改变搜索方向时才追问。

### 2. 多角度搜索

使用当前可用的 GitHub 工具、`gh` 或 `web.run`。组合以下角度：

- 领域或功能名称；
- 目标效果或用户体验；
- 可能的框架、协议或底层库；
- 必要时补充中英文关键词。

搜索结果只是候选，不是证据。无法联网或访问 GitHub 时明确报告，不虚构结果。

### 3. 核查候选

对高相关候选至少检查：

- README、截图或可运行演示；
- 许可证和归属要求；
- 最近活动、release 和维护状态；
- 安装方式、依赖和项目结构；
- 核心能力是否真的存在；
- 与当前技术栈的适配成本；
- 明显的安全、数据或供应链风险。

Stars 和 forks 只能作为弱信号。

### 4. 分类复用方式

- `base`：适合作为起始项目；
- `library`：适合作为依赖或引擎；
- `reference`：只借鉴交互、架构或实现思路；
- `skip`：许可、维护、能力或成本不合适。

不要在许可证不明时复制代码。优先遵循项目提供的安装和扩展方式。

### 5. 给出短名单

根据搜索空间给出少量高相关候选，而非固定凑数。每项包括：

- 仓库链接；
- 核心能力和技术栈；
- 复用分类；
- 许可与活跃度；
- 适配成本和主要风险；
- 推荐理由。

给出最快落地、最好长期质量或最适合学习的路线。只有路线会实质改变实现时才要求用户选择；用户已授权直接继续时，可采用最高适配且风险可接受的路线并说明判断。

## 后续边界

- 需要进入候选仓库、运行或改造时，按需使用 `project-orientation` 了解结构，再继续原任务，不把 Skill 切换当作停点。
- 不把搜索结果自动变成依赖。
- 仅调研不创建仓库或改代码；实现任务的仓库操作遵循原授权，推送另看授权。
- 不因找到“类似项目”就声称它满足当前需求。
