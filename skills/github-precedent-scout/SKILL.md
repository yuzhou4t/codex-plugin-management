# GitHub Precedent Scout

搜索并核查真正可复用的 GitHub 先例，帮助用户在采用、依赖、参考和自行实现之间做决定。本 Skill 只负责侦察和路线判断，不擅自克隆、安装或改代码。

## 工作流

### 1. 提炼目标

用一句话明确：

- 要解决的问题或目标体验；
- 必须满足的技术与许可约束；
- 用户要找完整成品、模板、库还是设计参考。

只有缺失信息会改变搜索方向时才追问。

### 2. 多角度搜索

使用当前可用的 GitHub 工具、`gh` 或 `web.run`。组合以下角度：

- 领域或功能名称；
- 目标效果或用户体验；
- 可能的框架、协议或底层库；
- 必要时补充中英文关键词。

搜索结果只是候选，不是证据。无法联网或访问 GitHub 时明确报告，不虚构结果。

### 3. 核查候选

对高相关候选至少检查：

- README、截图或可运行演示；
- 许可证和归属要求；
- 最近活动、release 和维护状态；
- 安装方式、依赖和项目结构；
- 核心能力是否真的存在；
- 与当前技术栈的适配成本；
- 明显的安全、数据或供应链风险。

Stars 和 forks 只能作为弱信号。

### 4. 分类复用方式

- `base`：适合作为起始项目；
- `library`：适合作为依赖或引擎；
- `reference`：只借鉴交互、架构或实现思路；
- `skip`：许可、维护、能力或成本不合适。

不要在许可证不明时复制代码。优先遵循项目提供的安装和扩展方式。

### 5. 给出短名单

根据搜索空间给出少量高相关候选，而非固定凑数。每项包括：

- 仓库链接；
- 核心能力和技术栈；
- 复用分类；
- 许可与活跃度；
- 适配成本和主要风险；
- 推荐理由。

给出最快落地、最好长期质量或最适合学习的路线。只有路线会实质改变实现时才要求用户选择；用户已授权直接继续时，可采用最高适配且风险可接受的路线并说明判断。

## 后续边界

- 需要进入候选仓库、运行或改造时，转交 `project-orientation`。
- 不把搜索结果自动变成依赖。
- 不创建仓库、不提交、不推送。
- 不因找到“类似项目”就声称它满足当前需求。
