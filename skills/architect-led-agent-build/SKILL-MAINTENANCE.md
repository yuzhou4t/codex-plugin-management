# Skill 维护：用户纠正与长期改进沉淀

**谁读**：编排助手（架构师）。在用户纠正执行方式、或提出可复用的流程改进之后加载。工人不读本文件。

主入口条件索引触发语：用户纠正 / 长期改进要沉淀进本 skill；本 skill 路径上的 commit 收尾，或判断是否同步 GitHub。

## 更新流程（按序）

1. **提炼可复用行为**  
   把对话里的纠正收成可检查规则（触发 → 核查 → 处置 → 恢复证据 → 何时问用户），去掉当次情绪、临时进度与可识别项目细节。

2. **区分通用 vs 项目专属**  
   - **通用**（多项目可复用的编排纪律）→ 本 skill 参考文档 / 必要时主入口一句索引。  
   - **项目专属**（某产品范围、某仓、某例程频率、某页责任人）→ 项目 SPEC、ADR、任务书或例程；**不**写入全局 skill 当默认。

3. **改冲突，不堆互斥旧条**  
   先搜现有条款：能改一处就改一处；新规则取代旧规则时删除或改写旧句，并在映射/维护笔记写明「取代何段」。禁止在文末不断追加与上文互斥的段落。

4. **守住渐进披露**  
   - 主入口：只保留始终需要的基本职责、默认原则、最小工单、**条件索引**。  
   - 诊断分支：放入 FAIL-* 或对应参考文件，必须含触发 / 处置 / 恢复验据。  
   - 启动必要条件（模型路由、AO 权限/派活）：保持「启动前读」，不要挪到「出错才读」唯一入口。

5. **回读检查**  
   - 所有链接指向真实存在的文件。  
   - 主入口索引能到达新规则。  
   - 无双源真相、无互斥并存。  
   - 工人路径仍只拿本票，不会因维护更新而被预塞整库。

6. **简短告知用户**  
   说明改了哪一文件、哪一条；不贴长 diff。写入前先加载 skill-authoring；正式正文优先经 UpdateSkill 更新，参考文件随之保存。主助手负责正式写入和回读，草稿可先落工作区。

## 硬边界

- **用户纠正 ≠ 越权授权。** 纠正「怎么编排/怎么验收」不自动授予 merge、部署、bypass、读凭据、非 AO 兜底，或其他仓库、其他 skill 的推送。本 skill 在已核实对应分支上的自动 push 只适用下文「累计 10 个本地 commit 后同步」；该授权不扩展到 merge 或部署。
- 不把项目监督频率（如每 30 分钟）写成全局 skill 硬编码。
- 不把单一项目 id、私有绝对路径、临时会话号写成默认。
- 专属技能若仅编排助手使用，保持在编排助手库；通用可共享技能走用户既有的共享流程。本 skill 推到已核实 GitHub 对应分支时按下文规则，不再就同一授权逐次请示。

## 累计 10 个本地 commit 后同步 GitHub

**谁执行**：编排助手在本 skill 的 commit 收尾时评估并执行。这是维护策略，不是守护进程、全局 git hook 或定时例程。本文不表示已经安装任何自动后台进程。

本规则不取消操作系统安全确认，也不取消 AO review。它只覆盖本 skill 在已核实对应分支上的自动 push。

### 计数起点

起点是本 skill 最近一次**成功同步到已核实 GitHub 对应分支**的远端提交。对应分支是本仓库里最近一次成功接收该同步的远程跟踪分支；发布这版规则时，该分支是仓库默认分支。

每次评估现查，不要把某一次提交 SHA、本机绝对路径、项目私有 id 或临时会话号写进本文：

1. `git fetch` 已核实的对应远程。
2. 在该远程跟踪分支上，取最新一个已经在远端、且变更了 `skills/architect-led-agent-build/` 的提交。这就是基线。
3. 基线提交本身不计入后续的 10 个。

成功推送并确认提交**已经在已核实对应分支上**、且远端 SHA 与本地提交一致后，下轮基线改为该远端 SHA。只推到独立同步分支或打开 PR、而提交还没进入该对应分支时，不重置基线，也不把默认分支说成已更新。

### 只数本路径上的真实 commit

只统计相对基线、对 `skills/architect-led-agent-build/` 有非空 diff 的本地 commit。不是 10 个文件，不是 10 条聊天，也不是 10 次无效 git 命令。在以该基线为祖先的当前分支上：

```bash
git rev-list --count <基线SHA>..HEAD -- skills/architect-led-agent-build/
```

`git rev-list` 配该路径时，只列出对该路径有变更的提交。空提交和只改其他路径的提交不会出现在列表里。基线不是当前分支祖先时，先 fetch；能非破坏 fast-forward 再对齐后计数。不能 fast-forward 时走下面的独立分支，不要 rebase 已推送历史。

### 收尾时怎么做

1. 从基线起累计达到 10 个此类 commit 时，在这次 commit 收尾**自动**按已核实对应分支做安全推送，不必再就同一授权请示。未满 10 则只做本地 commit。
2. 用户明确要求立即同步时，不等凑满 10，也不用空提交或无实质变更的 commit 凑数。引入本规则的那一次同步按立即同步处理；它进入已核实对应分支后，基线改为该远端提交，之后从 0 重新累计。
3. 推送前再 fetch。仅当可以非破坏 fast-forward 到已跟踪的对应分支，且待推送 diff 只含 `skills/architect-led-agent-build/`（以及为去掉本 skill 旧路径双源所必需的指针修正）时，才推到该对应分支。
4. 若必须先并入远端新提交、对应分支已受保护、无法安全 fast-forward，或 diff 夹带其他项目、其他 skill 或敏感文件：不要推该对应分支。把本 skill 的变更推到独立同步分支并打开真实 PR，不自行 merge。无法在不改写已推送历史的前提下拆开夹带内容时，停止推送并报告。
5. 禁止 force push、reset、rebase 已推送历史、跳过 hook。
6. 本授权只替换「本 skill、本仓库已核实对应分支、自动 push」范围内与之冲突的每次再批准要求。不扩展到 merge、部署、其他仓库或其他 skill。
7. 推送后用 `git ls-remote`，或再次 `git fetch` 后 `rev-parse`，核对远端 SHA。只有它与本地提交一致，且该提交已在已核实对应分支上，才把该 SHA 当作新基线。
