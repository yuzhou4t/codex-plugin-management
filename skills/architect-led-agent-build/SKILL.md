# 架构师带代理交付

负责把用户目标推进到约定的可用结果。保留技能名 `architect-led-agent-build`，作为新项目启动、旧项目继续、在途项目接手的同一入口。AO 承接委派与执行状态，提交、PR 和实际运行结果支撑验收。

## 先选当前入口

先沿用当前对话的目标、授权和决定，读项目指令、Git 状态及本次工作相关的入口。只补缺失信息，从当前节点继续后续步骤，确定一个当前动作后继续。

| 当前情况 | 直接进入 |
| --- | --- |
| 新项目，尚未完成方案讨论 | 进入 Matt 讨论，结合已有材料明确目标、方案和首个可验收成果 |
| 新项目，已有讨论结论或规格 | 读取已接受的决定，只补实际缺口，进入规格或任务书 |
| 已有项目，功能或实现方案需要讨论 | 结合现有代码和决定进入 Matt 讨论，形成该功能的方案后再安排实现 |
| 已有项目，迭代方案已确定 | 找到当前规格、已接受决定和运行入口，围绕本次变更补任务 |
| 有在途工人或 PR | 读原工单、会话、工作树及最新 PR，继续协调、恢复执行或复验 |
| 当前仅获准调查或讨论 | 按需用 Matt 讨论功能与方案，交回结论和待解决问题，按本次范围结束 |
| 自己是收到工单的执行者 | 按任务书实施、自测和交付，读下方执行者约定 |

识别入口时按需使用 `project-orientation`。仅在路线未定或用户要求查先例时使用 `github-precedent-scout`。这两个步骤结束后继续本次任务。

首次使用、跨机器接手或 Skill 更新后，核对目标 harness 实际读取的来源和修订版本。本 Skill 的维护源在插件仓 `skills/architect-led-agent-build/`，GitHub 与本机副本的差异应具体说明并按当前授权同步。文件已更新和 Bot 已加载分别核实；同一会话已核对且未更新时复用结果。

## 用户要求与职责

- 沿用会话中的授权。常规修改、验证、修复和已获准的交付直接推进。只有缺失决定会实质改变目标或动作超出授权时，才向用户提问，并继续独立部分。
- 用户点名的代理、模型和思考强度优先。助手及被派活代理禁止使用 Claude 系列或 Claude API，包含会落到 Claude 的 Auto/default。用户自己在其 IDE 中选择模型由用户处理。
- 所有委派，包括所加载 Skill 内的研究与审查代理，统一经 `ao spawn`。用户明确授权本次非 AO 路径时才采用相应替代。
- 架构师负责目标、协调、验收和授权内的集成交付。工人负责本票实施和自测。用户让你“派发后结束”，完成启动核对及交接后结束本轮；用户让你“盯到完成”，持续处理进度、返工和验收。
- 实现工单交付真实 PR。用户给定更窄的动作范围时按该范围交付并说明差异。调研和无仓库改动的数据任务按实际产物验收。
- 合并、推送基线、部署、对外发送和扩大权限各自沿用明确授权。Skills、AO approved 和已有工具能力都不追加这些授权。

## 1. 恢复项目现状与相关经验

新项目先确认根目录和 Git 边界，按 `git-finish` 建立必要基线。已有项目保护未提交、暂存和未跟踪内容，读取当前规格、任务与相关代码即可。

接手在途项目时，核对原任务对应的 AO 项目及会话、实际工作目录、分支、PR 最新提交和已完成检查。工人仍在执行时沿用该会话协调；已有成果时从缺少的复验开始；恢复前确认交接记录中的路径和进度仍与现场一致。新增派发前确认同一任务没有正在执行的负责人。已有 PR 的挂接、会话恢复和消息机制见 [AO 操作约定](references/ao-operations.md)。

读取与本次任务相关的已接受决定和历史教训。优先使用现有 SPEC、ADR、任务书、测试和项目经验记录。每条相关教训转成本票的一项可检查条件，并注明适用范围；旧数据、旧截图和历史测试只用于定位，当前结论由当前证据支撑。一次例外留在本票，跨项目反复适用的约定才进入通用 Skill。

这一步完成时，应知道当前目标、实际做到哪、谁在做、下一个动作，以及需要防止重现的具体问题。已有材料足够时直接继续，无需新建项目地图或要求用户复述。

## 2. 用 Matt 讨论功能与实现方案，再形成任务

新项目默认先进入 Matt Pocock 的讨论阶段。已有项目要增加功能、调整流程，或用户提出“这个功能怎么实现”“先讨论一下方案”时，也从这里进入。讨论围绕该功能展开，结合已有架构与决定明确需要解决的问题。用户已经说明目标时，把已有信息带入讨论，检查关键假设、方案取舍和验收方式。已有讨论结论或明确规格时，从原结论继续，仅补新出现的缺口。

1. 有工作目录且允许记录项目决定时，使用 `grill-with-docs`，结合 `grilling` 和 `domain-modeling` 理清目标、用语与重要取舍。尚无工作目录时使用 `grill-me`。当前仅讨论时按讨论范围处理。
2. 在讨论中明确谁使用这个功能、要完成什么、操作流程与数据状态如何变化、怎样接入现有系统、有哪些实现方案及取舍、第一版做到哪里、怎样验收。根据本次功能选择相关问题，对会改变方案的假设提出问题，并给出有依据的建议。可从代码或配置查证的事实先查，每轮最多 2–3 个实质问题。
3. 遇到必须看画面或运行才能判断的选择，按需使用 `prototype`，把试验结论带回原讨论。需委派时经 AO。复杂项目的关键决策尚不清楚时按需使用 `wayfinder`。跨目录或 harness 的交接使用 `handoff`。
4. 讨论得到的决定写入原有规格或适当的项目记录，说明选了什么、为什么、如何验证。跨多会话的任务接 `to-spec` → `to-tickets`，生成一份权威 SPEC 和带阻塞关系的工单，每票形成可独立验证的端到端成果。单窗小任务在讨论后直接写任务书。
5. 任务书准备好后进入 `ao spawn`，沿用本 Skill 的模型、权限及验收规则。Matt 阶段与 AO 派活的详细分流见 [AO 情境表](../ask-matt/AO-SITUATION-TABLE.md)。

阶段选择按实际需求进行，每次读取并加载当前主 Skill，调用其明确要求的基础方法。Grok Bot 有 Skill 加载工具时实际调用并核对返回。加载不可用时说明情况，读取可访问的 Skill 文件执行其讨论方法，并如实标为文件读取。若入口链接失效，先定位当前已安装版本。`setup-matt-pocock-skills` 仅在实际缺少配置时处理，先读已有 `docs/agents`。

沿用已确认的决定和统筹授权，规格与拆票直接推进。需要用户判断时集中询问会影响结果的取舍，保持已知部分继续。复用已有规格，改变决定时更新受影响段落并通知在途执行者，专项文档注明覆盖范围与替代关系。

讨论与工单最终应明确用户从哪个入口看到什么结果。有截止日期、受众或外部标准时纳入本票。演示任务列出关键画面及数字口径，界面任务写明实际内容、视口和主操作路径。

尽早检查凭据是否已设置、配额、数据和真实依赖是否可用。只读取必要配置，输出设置状态与非敏感模型名，凭据留在原有安全位置。受阻部分写明所缺条件，其余工作继续。

任务书写清以下内容，已有工单可直接补齐。

| 内容 | 要写到可执行的程度 |
| --- | --- |
| 目标与范围 | 用户可见结果、关联规格、负责文件、依赖和明确排除项 |
| 工作位置 | 仓库、基线、分支或 worktree、实际目标远程及 PR 目标 |
| 现有决定 | 本票必须沿用的选择、相关教训及对应验收条件 |
| 授权 | 修改、安装依赖、验证、commit、推本票分支、开 PR 分别是否允许 |
| 验证与交付 | 命令、真实入口、必要截图或样例、未验项和完成证据 |
| 续接 | 原 AO 会话或 PR、汇报对象、谁监控、完成后从哪一步继续 |

实现票明确允许阶段性本地提交；需要 PR 时写明本票分支推送和创建或更新 PR 的权限。任务书未明确的权限先由架构师根据已有授权补齐，再派发。

## 3. 经 AO 执行并持续推进

首次派发、恢复会话、更换执行者、启动 review 或改变执行权限前，读取 [AO 操作约定](references/ao-operations.md)。按其中的模型表显式选择模型、强度和 harness，并核对实际返回。每次派发使用中文可读标题，任务书必须在工人目录中可读。

工人按需使用 `tdd`、`diagnosing-bugs`、`pr`、`git-finish`、`domain-modeling` 等方法。只加载当前步骤需要且环境可用的 Skill。带内嵌派活的方法由架构师适配到 AO。

执行失败先看具体错误和当前状态，有依据地修复或重试。返工交回原会话，附上复现路径、期望结果和失败证据。重复失败时检查假设、依赖或任务拆分是否错误，再决定下一步。模型、权限或外部服务确实不可用时交回受阻部分与最小下一步，继续可独立完成的工作。

工人可以按任务书汇报进度、阻塞和 `checkpoint`。工人不得自行 `ao report --done`、宣布架构师验收通过、认领新票、合并或部署。

## 4. 复验到用户要求的入口

先核对最新改动和证据对应的版本，复用仍有效的检查结果。围绕本票验收条件读 diff、执行必要测试并走真实主流程。涉及页面或桌面应用时实际打开相关入口。用户要求预览、安装或更新本机软件时，在授权内完成到可打开使用的状态。

先前教训对应的检查必须在本票中有结果。构建通过、测试通过、PR/review、合并、部署和目标入口验收分别报告。被跳过的测试记为未验；真实外部依赖受限时，首行写明替代验证范围。回环地址、IP、域名及版本各自的失败应得到解释或保留为待验。

发现问题就回到执行步骤，修正后复验受影响部分。实现票由架构师自验后推进 AO review，按 [评审操作](references/ao-operations.md#评审与交付状态) 检查已有评审和提交结果。已获授权的合并、部署接着完成，并验证实际发布入口。超出授权的新增动作准备成可审阅结果后再询问。

完成依据是用户目标和实际证据。交付时给出可查看的产物或入口、版本、已验证结果及真实剩余事项。

## 5. 将教训接回下一轮

在修复得到验证后，判断哪些信息能防止下次重犯。

| 教训类型 | 最小落点 |
| --- | --- |
| 机器可以判断的错误 | 针对实际回归增加或收紧测试、校验，确认能识别旧缺陷 |
| 项目专属决定、视觉反馈或不可自动判断的取舍 | 更新已有项目规则或经验记录，写明触发场景、具体问题、正确做法和验证方式 |
| 多项目都适用的工作流缺口 | 提出通用 Skill 的定点修订，获得该 Skill 修改授权后写入并同步验证 |

已有代码、测试和文档足够表达教训时无需另写复盘。需要记录时合并同类、替换过期结论，保留有用的原因和失败做法。下一轮在步骤 1 检索相关项，再写进步骤 2 的任务书。复盘按实际收益进行，交付完成条件不追加用户复盘审批。

经验可以来自架构师自验或用户纠正。例如，页面曾在切换时出现整屏闪现，可把“主导航切换时检查报头位置和加载范围”写入相关 UI 工单。根据项目的交互目标判断这一检查是否适用。

## 6. 保存、交接和关闭会话

通过验证的独立阶段及最终交付前，按 `git-finish` 定点提交本任务持久改动。使用原任务书或交付记录保存进度，AO 保存执行关系。需要跨会话恢复时，在现有记录中补一个简短续接段，包含目标与已有授权、工作目录与分支、工单与 AO 会话或 PR、已验版本、待做项和下一步。已忽略的 `.architect/` 可放本机笔记；工人需要的文件放到其可读位置。写入前检查跟踪状态，保护凭据。

用户要求自动续接时，明确完成事件、接收会话和恢复动作，并验证消息送达及目标能继续执行。`checkpoint` 只交回进度；自动唤醒需要宿主实际支持。详见 [完成通知与续接](references/ao-operations.md#完成通知与续接)。用户指定派发后结束的，交回会话和下一步后结束本轮。

交付完成后关闭本票工人、reviewer 及不再需要的辅助进程，检查退出结果。已交付且确认为空闲的旧会话可一并收尾。用户明确保留、仍有依赖或已被继续认领的会话留给当前工作。具体保护范围见 [会话收尾](references/ao-operations.md#会话收尾)。

## 执行者约定

收到任务书的编码代理按本票的目录、分支、路径和权限实施、自测、提交并交回真实 PR。遵循模型约定和 checkpoint 规则，已有授权内的常规操作持续推进。缺少会改变行为的决定时报告具体阻塞，继续独立部分。交回提交、PR、实际验证及未验项，随后按任务书等待架构师处理。

## 使用效果

- “开一个新项目，你统筹，让 Cursor 做” → 先用 Matt 讨论目标和方案，确定首个成果，按规模形成规格与任务书，经 AO 派发并跟进约定的交付。
- “我想加这个功能，先讨论怎么实现，定下来再做” → 用 Matt 结合现有项目讨论功能流程、实现方案和验收，决定明确后按已有授权进入任务书与执行。
- “接手这个项目，已经有工人在做” → 核对原会话和 PR，从当前进度继续协调或复验。
- “上次切换会闪，这次别再出现” → 把相关教训加入本票，走实际切换流程验证，修复后保存可复用的检查。
- “派完你就结束，做完我再叫你” → 核对启动成功、交回工单与会话，结束本轮，下一次从原记录恢复。
