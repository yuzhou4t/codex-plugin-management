# 验收与范围失败诊断（按需加载）

**谁读**：架构师。读完后重验或开返修工单；工人只收返修票，不收本文件全文。

**适用问题**：⑩中「产出才算」在验收侧的用法；⑫当前要求完成后仅在明确持续完善授权下继续，禁止自动无限扩范围。并承接原 skill：工人自报不算、真实 PR、分层结论、本地≠整系统。

---

## 通用处置模板

每项依次执行：触发 → 核查 → 授权内处置 → 恢复证据 → 何时才需要用户。只读对应条目；不预加载其它诊断文件。

---

## 工人自报 / checkpoint 当验收

| 项 | 内容 |
| --- | --- |
| **触发** | 工人 `--done`、checkpoint、「已完成」话术被当成可合并/可结项 |
| **核查** | 架构师是否组织独立复验并亲读结果/关键产物；PR/review 状态；任务书勾选项 |
| **处置** | 不采信未核的自报结论；架构师按职责组织独立复验并亲读证据 + `ao review`（或已记录的替代原因）。工人禁止自行宣布验收完成 |
| **恢复证据** | 架构师签字的分层结论与证据路径 |
| **才问用户** | 需要新增 merge/部署授权时 |

## 局部通过冒充整票 / 整系统

| 项 | 内容 |
| --- | --- |
| **触发** | 单测/单页/单 API/旧包预览被写成「系统完成」；历史会话恢复到 idle 或仅开 PR 就被当成「已验收就绪」；前后端未接；回环成功盖过域名失败等 |
| **核查** | 原任务逐项验收点是否全覆盖；历史票是否仍缺补完、返修、独立复验、适用的 PR/CI/review；后继产物是否逐项覆盖旧要求；主流程与入口是否真实走过 |
| **处置** | 结论必须分层标明：本地代码/测试｜PR·review｜合并｜部署及目标入口。路径失败未解释清楚则保留失败/待验。缺真实外部条件时完成独立部分，并在结论**首行**标明替代验证范围。若 AO review 不可用，可用「架构师自验 + gh PR 状态」替代，但须在 `.architect/` 写明原因，不得假装已 AO approved |
| **恢复证据** | 逐票验收矩阵 + 精确产物/hash + 返修复验结果 + 适用的 PR/head/检查/review + 真实就绪状态。恢复成功只证明会话可用；未通过项继续返修，旧失败不得改写为通过；合并/部署与就绪分开，未经合并不自动判未就绪 |
| **才问用户** | 外部依赖/密钥/域名等真实阻塞 |

### 场景钩子：局部测试过、整体缺前端

按本条：验收报告首行写明「后端/单测有限通过；前端集成未验」；开前端集成返修票（或交前端负责人）；禁止把有限包写成整系统完成。

## 真实 PR 语义

| 项 | 内容 |
| --- | --- |
| **触发** | 无 PR 的实现票进「就绪」；或 `claim-pr` 被当成已开 PR；或说明性文档冒充代码交付 |
| **核查** | 托管平台上的 PR URL、head、与工作分支是否一致 |
| **处置** | 实现类必须真实 PR；`claim-pr`/`spawn --claim-pr` 只挂接已有 PR，不创建、不检出。调研类按交付物验收，不强开空 PR |
| **恢复证据** | 可打开的 PR + 架构师自验记录 |
| **才问用户** | 目标远程/仓未在票面写明且无法从项目约定唯一确定时 |

## 就绪标准不清 / 旧票无限拖延

| 项 | 内容 |
| --- | --- |
| **触发** | 反复报检查点却不收口；修好评审启动就标完成；不断把新要求追加到旧票；为减少待办而归档未完任务 |
| **核查** | 原验收清单、全部证据、blocking缺陷、准确交付版本、独立复验与适用评审是否齐全；阻塞来自产品、运行环境还是未约定外部条件 |
| **处置** | 为仍有效的要求逐项补完→验证→修复→复验→架构师终验，持续推进到本票就绪。丢稿、串作品、权限泄露、主流程中断属于阻塞；小瑕疵按实际影响记录分流，不要求无限完善。新增要求另列有界票；已明确预留/后配的外部条件单列未测，不假装真验，也不无限阻塞能独立交付的约定范围。评审启动故障按已有授权修环境，再取得真实结论并处理发现；启动成功不等于通过。失效旧票仅在有归档授权时按 AO 操作的分流规则处理 |
| **恢复证据** | 原要求全覆盖、目标版本对应、适当测试及实际主流程证据、阻塞缺陷返修复验、架构师亲读终验、适用 PR/检查/review。实现票与调研票按各自交付判断；单票就绪与整产品可体验、合并、部署分别报告 |
| **才问用户** | 原要求实质冲突且依据无法确定、新增权限/依赖超出授权、或确需用户填密钥/外部操作；常规返修不逐步请示 |

## ⑫ 持续完善 vs 范围膨胀

| 项 | 内容 |
| --- | --- |
| **触发** | 当前用户要求尚未做完却扩新大方向；或做完后在**无**「继续完善」授权时自动开无限重构；或把一次纠正理解成永久扩大 merge/部署/权限 |
| **核查** | 用户是否明文授权「做完当前要求后继续完善到满意」；完善边界是否写进 SPEC/非目标 |
| **处置** | **先完成本轮明确要求与验收。** 仅当用户明确授予持续完善时，再在约定产品边界内分派后续票。未授权则结项汇报，不等待中自行扩 scope。用户纠正沉淀见 [`SKILL-MAINTENANCE.md`](SKILL-MAINTENANCE.md)，**纠正 ≠ 越权授权** |
| **恢复证据** | 本轮验收勾完；若有后续完善，有单独授权记录与有界工单 |
| **才问用户** | 完善是否继续、边界何在、是否授予合并/上线 |

## 合并与权限（验收后）

不自动 merge/推基线/部署。沿用已有授权；新增动作只确认新增部分。AO approval ≠ 平台 approval ≠ merge 权。
