# 停滞与恢复

先看原任务、最近实际动作、相关产物和安全可读的错误信息，形成具体判断，再做小范围修复。优先原会话的官方发送、恢复或续跑接口，保留现场，避免重复执行者或无依据重启。恢复后以本任务的新动作或产物确认，回执只能证明接收。

| 情境 | 处理 |
| --- | --- |
| 未完成却 idle、退出或被归档，出错后只汇报 | 查缺项和在途依赖，恢复仍有效的任务；能在授权内修就继续。小批结束后核对剩余目标，仍有已授权工作就接着做。停止重复重启后仍须给出有依据的接续办法或真实阻塞。 |
| working、accepted 或指令已发，却无实质动作 | 对照预期目录、最近文件、测试与 PR，向原会话查阻塞；没有新证据就不能说执行恢复。不要连续发送空指令冒充推进。 |
| 启动几秒就退出，没有接票 | 查公开错误、模型参数、工作目录与权限，按 [模型路由](MODEL-ROUTING.md) 修复；重新核对接票及首个实质动作，启动失败本身不证明模型不可用。 |
| 机器或通道暂时不可达 | 区分网络波动、明确拒绝、认证和审批。对暂时故障按项目预算间隔重试，先用同机器只读探针；写操作重试前查是否已成功。保留恢复点，继续独立工作，必要时由已有监督接续。明确权限拒绝不能按网络故障绕过。 |
| 夜间、周末或无人回复就自行停工 | 沿用项目的持续接续与资源约定。监督频率属于项目，不写成全局每 N 分钟或永不收尾。只有实际建立且运行过的监督才可称在工作。 |

凭据、强制审批、外部配额、核实后不可用的指定模型或新增权限确需用户处理时，说明具体阻塞；不要把短暂失败直接交还用户，也不要无依据无限重试。已明确暂停的任务保持暂停。

## 对用户说明实际状态

按证据区分正在核查、已安排或接收、实际执行、受阻和 [验收完成](FAIL-ACCEPTANCE.md)。监督助手在核查不等于执行者在工作；实际执行要有近期相关命令、分析正文、文件、测试或 PR 活动，并能说明最近一步和时间。小批结果只代表该批次，配置监督不等于已经持续执行。

未完成的空闲会话先接续；能否关闭见 [会话收尾](AO-OPERATIONS.md#会话收尾)。
