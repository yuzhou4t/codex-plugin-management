# 按项目进度选择做法

以下是方向，不是每次必走的步骤。复用现有规格和任务记录，缺什么补什么；已有项目先核对相关代码、Git、AO、PR 和验证结果。

| 当前情况 | 该推动的结果与沟通方式 |
| --- | --- |
| 新项目或尚未定下的新功能 | 把目标说成一条用户操作，说明谁使用、得到什么、本轮交到哪里，以及时间或外部验收要求；演示明确关键画面与数字口径。给出推荐与关键取舍，明确可验证结果后继续。 |
| 比较前端或交互方案 | 用同一组实际内容、同一条操作比较有实质区别的方案，说明取舍和推荐；保留已定风格与功能。版式可用图，操作与动画用可体验原型，按需求覆盖手机和桌面。记录最终选择或组合，未决部分不拖住独立工作。 |
| 做功能、前端、后端及连接 | 将页面、接口、数据和失败处理对应到同一条操作，明确接口约定与联调负责人。尽早查真实依赖，区分示例和本轮必须接通的服务，优先打通一条完整路径。向用户说明先能体验什么、哪些可并行。 |
| 已授权实现或已有执行者 | 接续原任务、会话和 PR，经 AO 分配清楚的责任。跟进实质产出并处理停滞，持续做到验收和交付；用户只要求派发时，核实实际启动并留下续接信息即可。 |
| 中途增加想法或发现问题 | 原要求没实现就回原任务修复，PR 仍开放时更新它，已合并则跟踪修复 PR。方案改变就更新原决定并通知相关执行者；独立新功能单独安排。只有会改变既定交付承诺且取舍未明时才请用户决定。 |
| 已有可验版本 | 按 [验收标准](FAIL-ACCEPTANCE.md) 完成实际操作、复审和约定交付。用户体验后的反馈进入原任务修复或新功能讨论。保留结果与续接点，按项目约定收尾。 |

任务记录足够让另一位执行者接手即可。通常要说明目标与范围、原决定、负责人、目录和分支、可改位置、接口依赖、可验证结果、允许的 Git/PR 动作及目标远端；已有会话或 PR 一并关联。字段可合并，不要求固定模板或另造一套账本。

## Matt 与其他技能

需要深入讨论、形成规格或拆分任务时，按同库 `ask-matt/AO-SITUATION-TABLE.md` 选当前主方法。典型选择是有项目资料用 `grill-with-docs`，无目录用 `grill-me`，复杂取舍用 `wayfinder`，跨会话实现按需用 `to-spec` / `to-tickets`。以当前环境实际可用技能为准，方向已清楚的小任务直接继续。

真正加载或读取所选技能再使用；不要声称加载了不存在的工具。`tdd`、`diagnosing-bugs`、`pr` 等方法可交给执行者。含内置委派的 `research`、`code-review`、`prototype`、`wizard` 由架构师适配到 AO，避免另开派工路径。现有项目约定优先，缺少 setup 才补，交接和回顾按需用，不增加交付关卡。

持久实现按 `git-finish` 保存版本，讨论不必建仓。内部任务资料放合适的私有位置；忽略规则不会移除已跟踪文件，密钥不进入任务书、日志或交付证据。
