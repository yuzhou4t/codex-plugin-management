# Project Orientation

在动手前从当前项目表面建立一个小而准确的地图：项目做什么、如何运行、关键边界在哪里、怎样验证用户当前要求。

## 工作流

### 1. 确认项目根

- 默认使用当前 `cwd`，除非用户明确指定其他目录。
- 检查根目录、仓库元数据、`AGENTS.md`、`CLAUDE.md`、`README.md`、相关 `docs/`、构建清单和锁文件。
- 存在多个候选根时，以包含应用入口或仓库元数据的目录为准，并说明假设。

### 2. 先读项目指令

按顺序读取：

1. 当前路径生效的 `AGENTS.md`、`AGENTS.override.md` 或 `CLAUDE.md`；
2. `README.md`；
3. 与本次任务直接相关的架构、运行、数据或设计文档；
4. 实际入口、配置和测试。

不要批量读取所有文档。文档与代码冲突时，以当前用户指令和已验证的运行或代码状态为准，并报告差异。

### 3. 建立任务所需地图

只记录与请求相关的信息：

- 项目用途和当前状态；
- 技术栈、入口和模块所有权；
- 数据、接口或状态流；
- 运行命令、环境依赖和必要权限；
- 最窄的验证路径；
- 已知风险或不确定性。

分析请求只返回地图；实现请求则在确认边界后继续做最小改动。

### 4. 安全运行和预览

- 优先使用项目已记录的命令；推断出的命令要明确标注。
- 静态问题不必启动服务。
- 使用已占用端口前，核实监听进程和项目归属。HTTP 响应本身不能证明归属。
- 端口属于其他项目时，选择空闲端口并报告实际 URL；不要终止无关进程。
- 记录本任务启动的进程，只停止自己拥有的进程。
- 根据任务选择最窄的 build、test、lint、健康检查或浏览器验证。
- 网络、密钥、GUI 或权限是必要条件时，明确指出。

### 5. 保持职责分离

- 用户明确要求同步项目文档或交接材料时，使用 `project-docs-sync`。
- 用户明确要求 Git 收尾、提交或推送时，使用 `git-finish`。
- 用户明确要求先寻找 GitHub 先例时，使用 `github-precedent-scout`。

本 Skill 不自动同步文档、写记忆、提交、推送或发布。

## 输出

分析型定向报告保持简短：

- 项目目的；
- 技术栈；
- 关键文件；
- 运行或检查方式；
- 建议的下一项验证；
- 风险或阻塞。

实现任务的最终报告由实际修改和验证结果决定，不重复完整项目介绍。

## 安全底线

- 不把长 README 当作当前事实，核对实际入口。
- 不为简单静态问题启动服务。
- 不为抢占端口使用宽泛 kill 命令。
- 不把简单项目擅自重写成新框架。
- 不创建用户未要求的文档、记忆或 Git 历史。
- 不修改无关文件。
