# Project Docs Sync

让项目文档与当前代码和已确认决策一致。只同步用户明确纳入范围的项目和文档，不把一次会话变成全库清理。

## 边界

- 只处理项目内的 README、项目指令、docs、runbook、架构、集成和交接文档。
- 不读取或修改 `~/.codex/memories`、`MEMORY.md`、其他 Agent 记忆目录或全局用户配置。
- 不自动提交、推送或发布；需要 Git 收尾时交给 `git-finish`。
- 不因发现相邻问题而扩大范围。
- 删除文件、大规模重排或跨项目同步必须有明确授权。

## 工作流

### 1. 确定范围

确认：

- 项目根；
- 用户要求同步的事实或里程碑；
- 目标读者；
- 明确纳入范围的文档。

若用户只指定一个文件，只处理该文件及验证它所必需的证据。

### 2. 检查真实状态

先读项目指令和目标文档，再检查与待同步事实直接相关的代码、配置、测试或运行结果。优先级为：

1. 当前用户指令；
2. 已验证的代码或运行状态；
3. 当前项目文档；
4. 历史叙述。

文档与代码冲突时，先确认代码是否代表已经完成并验证的状态；不要把未完成实现写成现状。

### 3. 选择正确落点

按受众放置信息：

| 内容 | 首选位置 |
|---|---|
| 项目用途、安装、最短运行路径 | `README.md` |
| AI 必须遵守的边界、命令和禁区 | `AGENTS.md` / `CLAUDE.md` |
| 数据流、模块职责、设计取舍 | 架构文档 |
| 外部调用方式、接口、错误码 | 集成指南 |
| 部署、监控、恢复、环境变量 | runbook |
| 当前状态、剩余工作、接手入口 | handoff |

不要把 Git 历史或会话流水账塞入项目指令。已存在的事实应就地更新，避免追加重复章节。

### 4. 执行最小同步

- 先搜索同主题内容，再局部修改。
- 保留现有结构、术语和写作风格。
- 只写已验证或明确标为计划、实验、未知的内容。
- 使用绝对日期表达会过期的时间信息。
- 只有在现有文件无法清晰承载内容时才新建文档。
- 不清理与本次同步无关的旧文档。

### 5. 验证

检查：

- 文档中的路径、命令、脚本、环境变量和接口确实存在；
- 同一事实在目标文档之间没有冲突；
- Markdown 标题、链接、表格和代码块结构完整；
- diff 只包含本次同步需要的行；
- 没有写入秘密、本地状态或未经确认的结论。

能安全运行时，执行文档中最关键的命令或最窄静态检查；不能运行时明确说明未验证项。

## 交付

简要报告：

- 实际修改的文件及每个文件的变化；
- 使用的代码或运行证据；
- 未处理的范围及原因；
- 仍可能过期或需要用户决策的内容。

若审查后无需修改，明确说“当前范围内文档已经与已验证状态一致”，不要制造改动。
